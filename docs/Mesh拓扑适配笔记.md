# 小米 Mesh 拓扑适配笔记（无线/有线回程）

> 状态：**预适配设计**（无实机，拓扑结论基于小米 Mesh 官方机制推演，全部待实机验证）。
> 套件当前覆盖两种拓扑：独立主路由、独立 AP/中继。第三种——小米 Mesh（多节点组网）在此预设计。
> 典型场景：BE3600 作主节点 + AX3000E 作子节点（小米 Mesh 支持同品牌混型组网）。

## 拓扑与角色

| 拓扑 | 网关/ DHCP | DNS 去广告挂点 | 已支持 |
|---|---|---|---|
| 独立主路由 | 本机 | 本机 dnsmasq | ✅ |
| 独立 AP/中继（上级另有网关） | 上级路由 | 本机 dnsmasq（上级 DHCP 把 DNS 指过来） | ✅ |
| **小米 Mesh（无线/有线回程）** | **主节点** | **主节点 dnsmasq** | ⏳ 本文档 |

**核心结论：Mesh 里子节点不做 DHCP、不配 DNS——去广告只部署在主节点。**
子节点在 Mesh 中本质是受管的无线 AP：客户端 DHCP 与 DNS 均由主节点下发，子节点上配 dnsmasq 是无效的（客户端根本不会问它）。这与"独立 AP 模式"是两回事，别把 AP 面板那套 DNS 配置直接搬到子节点。

无线回程与有线回程的区别**不影响 DNS/去广告设计**，只影响监控面（回程链路速率/信号是 Mesh 特有的健康指标，见下）。

## 各组件的 Mesh 化方案

| 组件 | 方案 | 备注 |
|---|---|---|
| SSH 解锁 | 逐节点独立解锁（每个节点有自己的管理页与 stok，注入方式同单机） | 主/子节点固件版本应一致，避免组网兼容问题 |
| auto_ssh 三层自愈 | **逐节点安装**，但子节点的恢复块跳过 DNS 段（无 dnsmasq 职责） | 需要按节点角色分流的配置开关 |
| DNS/去广告体系 | **只在主节点**部署（上游池/列表/自定义屏蔽/查询日志） | 面板 DNS 相关动作在子节点上应禁用并说明原因 |
| 面板 | 单面板多节点：节点列表（主/子角色、各自健康度），DNS 类功能仅对主节点可用 | 现有架构一个面板一个 `ROUTER_HOST`，多节点是结构性扩展——主节点连接复用现有逻辑，子节点连接池新增 |
| WiFi 面板动作 | 每节点各自的信道/功率即时切换；Mesh 漫游（802.11k/v/r）与频段引导由固件统一管理，面板不做独立开关 | 与单机"即时切换不持久"的边界一致 |
| 备份/恢复 | 逐节点独立备份 | 恢复白名单机制复用 |

## Mesh 特有的监控面（待实机确认接口）

- **回程链路与速率**：有线回程看 2.5G/1G 协商速率，无线回程看回程 RSSI 与协商速率——这是判断组网健康的第一指标
- **漫游事件**：客户端在主/子节点间的切换记录（如固件有日志/命令可读）
- **每节点负载**：复用现有 CPU/内存/连接数采集，逐节点展示

## 落地顺序（实机到位后）

1. 主节点解锁 + 部署全套（等于现有"独立主路由"流程）→ 验证子节点入网
2. 子节点解锁，装分流版自愈（仅 SSH/开机钩子，无 DNS 段）
3. 面板加节点管理：多 `ROUTER_HOST`、角色标记、DNS 功能门禁
4. 补 Mesh 监控面（回程/漫游，按固件实际暴露的接口，实测一个加一个）

> ⚠️ 待验证清单：子节点能否独立开 SSH 并保持（Mesh 配网/升级是否会重置）、主节点 dnsmasq 版本与 `/#` 语义、子节点上 uci wireless 的可控范围、回程速率读取接口。
